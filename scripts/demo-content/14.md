## Problem

Postgres keeps only lifetime sync totals for each account (`analytics.sync_stats`). It has no record of when a sync happened. So the admin page cannot show how sync success changes by day, week, or month. The team needs this number to check whether the sync retries help on slow networks.

## Rule for this repo

The server stores sync analytics as small daily counters, not as one row per sync. The database has a 1 GB disk. A full sync log would grow by about 400 MB a year at real traffic.

## What to do

* **Migration** `000016` (renumbered after [DEMO-71](https://example.com/demo/issue/DEMO-71) took 13 to 15)**:** add `analytics.daily_sync_stats`. It has one row per UTC day, client kind (Desktop or Web), and network class (0 to 5). Its counters are attempts, successes, partial syncs, timeouts, and the sum of sync times in ms.
* `Store.RecordSync` in `internal/sync/workflow.go`: upsert the daily row in the same transaction. The upsert runs after the receipt check, so the server does not count a retried sync twice. Read the client kind and network class in the existing `SELECT`.
* **Counting rules:**
  * A Desktop sync succeeds when every change reaches the server.
  * A Web sync counts as partial when at least 90% of its changes reach the server. When a sync has 0 changes, only a clean finish counts as a success.
  * A timeout is a failed sync, and its sync time is the full time limit.
  * Test accounts stay excluded.
* **Admin API:** add a new `GET` endpoint for the sync series, separate from `/v1/admin/sync/stats`.
* **Dashboard card:** a card two columns wide on desktop and one column on phones. It has a Desktop/Web toggle, a Day/Week/Month/All-time toggle, and paging like the "New accounts" card. It has two tabs:
  * **Success rate:** one line for each network class, plus an overall line.
  * **Sync time:** the average sync time for each network class.

+++ Detail: decisions, sizing, and limits

**Size estimate.** One sync row with an index takes about 110 bytes. At 100 accounts a day with about 100 syncs each, a full log grows by about 3.6M rows a year. That is about 400 MB. The daily summary has at most 12 rows a day, which is under 1 MB a year. Traffic today is at most 3 users at a time.

**Write cost.** Each sync adds one upsert to a counter row. No indexed column changes, so Postgres updates the row in place. It already does this for `sync_stats`.

**Network grouping.** Each sync counts under the network class the client reported at sync time. When a laptop moves to a faster network, old days keep the old class. The `calibrate` command still compares lifetime totals with the current class.

**History.** The chart starts on the deploy day. The older lifetime totals have no dates, so the server cannot split them by day.

**Periods.** Days and weeks use UTC, like the "New accounts" card. Week, month, and all-time are sums of daily rows. All-time shows totals since deploy, and its chart uses monthly buckets.

**Not in scope.** This ticket does not chart single syncs against note count. The follow-up ticket adds a sync log that keeps rows for 30 days, which stays at about 35 MB.

**Original request.** A "failed vs succeeded" number for syncs, for all network classes together and for each class. It is a dashboard card two columns wide, with day, week, and month views. Desktop syncs succeed or fail. Web shows how close each sync gets.
