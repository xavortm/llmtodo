Two speed ideas left over from [DEMO-140](https://example.com/demo/issues/DEMO-140), which cached rows around the scroll position. Neither idea is proven yet.

## Validate first

Do not build either idea on trust. For each one:

1. Measure the cost it targets, on its own. If the cost is inside the noise, close the item and write down the number.
2. Only then build it, and measure again.
3. Keep the change only if the gain is clearly larger than the noise and the code does not get harder to read. Otherwise revert it and record the result here.

The machine was busy during the [DEMO-140](https://example.com/demo/issues/DEMO-140) runs. Single runs of the same code ranged from 0.59 ms to 0.82 ms. Take the measurements on a quiet machine, in turn with the commit before, three runs each. See `BENCHMARKS.md`.

## 1. Draw the list rows as one quad per cached block

**What** [DEMO-140](https://example.com/demo/issues/DEMO-140) **measured.** The GPU frame median went from 0.570 ms to 0.671 ms. Each pixel of the list now finds its row block and its layer before it reads the cached text. A quick test without the block math read about 0.52 ms, but that reading was inside the noise.

**Idea.** Draw one quad per block of the row cache, all in one instanced draw call. The vertex shader works out the block and its layer. The pixel shader only reads the cached text, as it did before the blocks.

**Doubts to check before building.**

* The gain is 0.1 ms at most, and the frame already uses under a tenth of the 8.3 ms budget. This may not be worth more code.
* The list past the row cache is no longer drawn. It would show blank space and not the empty row style, unless something else fills it.
* Shared quad edges must land on exactly the same pixels, or seams show. The seam test from [DEMO-140](https://example.com/demo/issues/DEMO-140) must still pass.
* The list draw stops at the status bar today. The quads must keep that saving.

## 2. Time the per-frame cache check on the CPU

**What is missing.** The benchmark column "Frame build on the CPU" does not include `RowCache::update`. On a frame where nothing changed, it compares 72 blocks and does no GPU work. I expect well under a microsecond, but I did not measure it.

**Idea.** Add that check to the benchmark, as its own number.

**Doubt to check.** This adds a measurement, not a speed-up. It is worth keeping only if the number is large enough to watch. If it reads a few dozen nanoseconds, note the result in `BENCHMARKS.md` and do not add a column.

## Not in this task

Deleting the two merged branches was on the same list of ideas. It is cleanup, not speed work, so this task leaves it out.
