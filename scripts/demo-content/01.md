## Problem

Every time the list view opens, Demo App calls `NoteService.loadPage` (`src/notes/page.rs`). It loops over 40 notes and calls `store.fetch(id)` once for each note. That makes 40 calls in a row, and each call makes two round trips: one `SELECT id ... LIMIT 1` and one separate `fetch_body` join. The list can wait for 80 network round trips before it shows anything. [DEMO-12](https://example.com/demo/issues/DEMO-12) had the same kind of bug in bulk archive, which sent one request per row. This bug sits in the list view, which people open all the time.

`NoteService.saveOrder` has a smaller version of the same bug. It writes `note_positions` rows one at a time in a loop, not in one statement.

## Rule for this repo

Do not ask the database for each list view when the data changes slowly and people read it often. A notes folder can grow to 20,000 notes, so the server cannot keep every folder in memory. One list page only needs 40 notes. Keep a small **page cache** in memory for the folders people open, and do not load whole folders.

## What to do

* Add a cache in `src/notes` named `PageCache`, around `Store`. It holds the first 200 notes of each folder that someone opened, and it refreshes on a timer. The default timer is 5 minutes.
* Each refresh runs one query per folder: `SELECT ... FROM notes WHERE folder_id = $1 ORDER BY updated_at DESC LIMIT 200`, with the note bodies. It does not load the whole table. 200 notes is far more than the 40 that one page shows, so many open windows can read from the same cache.
* Refresh a folder only while a laptop has it open. A folder enters the cache on first use and leaves it after 10 minutes with no reads. An idle server should not pay for queries.
* `loadPage` and `countNotes` read only the cache. They pick and filter notes in memory, with no database call and no second `fetch_body` round trip. If a folder has fewer cached notes than a page needs, read the rest from `Store` and log it. Do not fail the page.
* `NoteSource` keeps the same interface. Pass the new cache to `NoteService` in place of `Store`, so the code in `src/notes/service.rs` does not change.
* `pin` and `archive` still write straight to the database. Writes do not go through the read cache.
* In `saveOrder`, write all `note_positions` rows in one `INSERT ... SELECT unnest(...)` statement. This change is not part of the cache, but the same pull request can carry it.

## Done when

* Opening the list view runs no database query for notes when the folder is in the cache.
* One refresh reads at most 200 rows in one query, however large the folder is. Refreshes run only while a laptop has the folder open.
* A new or archived note shows in the list within one refresh, about 5 minutes. Sync already pushes changes from the same laptop at once.
* `saveOrder` writes all positions in one statement.
* The current note service tests pass. New tests show that `loadPage` and `countNotes` skip the database for a cached folder. One more test shows the fallback when the cache is short, and one shows that the cache size stays the same for a large folder.

+++ Detail: why a page cache and not a full copy of the table

A folder can hold 20,000 notes, and each note can have a long body. A full copy of every folder in every server's memory does not scale. A copy of the first 200 notes per open folder does. A full copy would also need its own rules for when it goes stale. One page needs 40 notes, so a small cache with a timer removes the database call at a fixed, small cost.

The cache keys on `(folder_id, sort)`, because `loadPage` filters by folder and by sort order. One shared cache for all folders could leave a small folder empty even when the cache holds 200 notes. Keep entries only for folders that someone opened. Do not build one for every folder in the database.

Tie the refresh to open folders and not to a fixed timer for everything. An idle server then sends no queries every 5 minutes. The product owner asked for this rule, and it also keeps costs down at night.

Page size is 40 notes: `PAGE_SIZE = 40` in `src/notes/page.rs`. The list view calls it from `src/notes/service.rs:212`, and the debug page calls it from `src/notes/debug.rs:58`. The database runs on another host, so each round trip adds real network delay. 80 round trips in a row can easily add several seconds before the list shows. [DEMO-12](https://example.com/demo/issues/DEMO-12) fixed the same kind of problem and cut bulk archive from 20 seconds to under 1 second. This fix goes further, because it removes the database read from the list view.

The product owner accepted one trade-off. A cached page can be up to 5 minutes old when a note changes on another laptop and sync has not pushed it yet. In that case the list shows the old title until the next refresh or the next sync event. Sync events arrive within seconds in normal use, so most people never see an old title. Two laptops that open the same folder still each sort and filter the page on their own. No more work on stale pages is needed in this ticket.

The import path, `Importer::run` in `src/import/notes.rs`, has the same one-row-per-request shape. It calls `insert_note` once for each imported note, and each call opens and commits its own transaction. Only admins use import, and they use it rarely, so this ticket lists it as a second item. Fix it in the same pull request if it is easy.
