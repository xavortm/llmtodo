## Decided by the owner (chat, 2026-10-20)

The open list running out is normal, not a problem. The open list is small, so the user sees progress fast. The other lists are larger, and background sync carries them later. The owner adjusts the sample account to tune it. `docs/PRODUCT.md` holds the rule.

So this ticket is now a task for the sync tools. The model must count the payload growing as the open list runs out. Today every batch stays 10 KB, so the model's times past minute 25 are too fast. The proposal in [DEMO-44](https://example.com/demo/issue/DEMO-44) is too small after that point.

The test script of [DEMO-44](https://example.com/demo/issue/DEMO-44) found this problem on 2026-10-20.

## What happens

* The sample account holds about 165 MB. The script synced the open list by minute 25, after about 82 MB.
* The next notes then sat in lists 120 positions down. The sync rate fell from about 85 KB/s to 20–35 KB/s.
* The script finished the Archive section at 2:49. The model said 1:04.
* A queue that long does not fit Retry 1's 30-second window, so retries start only at Retry 2.
* The sync model treats the open list as endless, as the owner chose for [DEMO-44](https://example.com/demo/issue/DEMO-44). A full sync needs about 3,200 to 3,800 MB, based on the batch sizes the owner picks in [DEMO-44](https://example.com/demo/issue/DEMO-44).

## Needs the owner's choice

How does the first sync bring enough notes into the open list? Some ways:

1. Put more notes in the open list at the start, or sort the most-used lists first.
2. A prefetch step, or a later server job, moves far notes closer. The model then needs the prefetch step.
3. Accept longer syncs, and make the batches smaller as the syncs grow.

[DEMO-49](https://example.com/demo/issue/DEMO-49) limits the account size, so the answer may belong there.
