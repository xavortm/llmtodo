**Problem**
I read the sync server code on `origin/develop` at `4c5d6e7` and found no single big bug. But several paths do more Redis and Postgres work than they need, and most of that work runs while the server holds a workspace lock. Under load, people will see lock timeouts on saves, a slow sweeper (`max_lag`) and waits for Postgres connections. CPU will not be the problem.

**PR link:** [Keep Postgres and locks off the sync hot paths (DEMO-93)](https://example.com/demo/pulls/93)

**Measured** with 20 callers at once and a local Redis: GET workspace while editing went from 455 to 5,048 requests per second, and p99 from 405 to 9 ms. Resume went from 464 to about 4,500 requests per second with no lock timeouts. The sync poll p95 went from 5–9 ms to 3.7 ms. A live `SyncState` is 17 KB with real note lengths, and it stays one key.

**Rule for this repo**
No Postgres call belongs inside a Redis lock unless the lock is what makes it correct. A read must not take a lock. Look first, and lock only when something must change. Build a workspace view once per request and use it again.

**What to do**

* `NoteStore::record_edit`: stop pruning `analytics.edit_receipts` in every save transaction. Prune once an hour from the sweeper. Put the up to 3 `record_edit` calls of one sync into one transaction, or save them after `save_state` returns. The receipt key already makes a repeat save safe.
* `Service::workspace` and `authenticate`: `enforce_deadlines` calls `take_lapsed_invite` and `finalize_if_closed`, and each one takes the workspace lock on every read of an active workspace. Check the loaded state without a lock, and lock only when a deadline is due or the workspace is closed.
* The server builds `view_with_members` twice per change: once in `broadcast` and once for the HTTP reply. Each build does its own `GET sync:` and presence `EVAL`. Let `broadcast` return the view. `leave` reads the state blob three times.
* `cache::Locker::acquire`: replace the 20 ms SETNX loop, which costs up to 150 calls per waiter, with a random backoff or a release signal. Waiters pile up on the queue lock in `poll_sync`, which every client calls every 2 seconds, and on the workspace lock when a sync closes.
* `run_sweep_tick`: handle due workspaces with a fixed limit of about 8 at once, not one by one. Do not `break` out of the tick when one lock is busy.
* `deps::connect_postgres`: set `max_conns`, `min_conns`, `max_conn_lifetime` and `max_conn_idle_time` from config. Do not rely on the library defaults, which give 4 connections on a small host.
* Measure the size of `SyncState`. It carries about 40 recent notes with titles and tags, and the server encodes it on every read and write, 3 or more times per action. If it is over 20 KB, keep the recent notes in their own key and write it once at sign-in.

**Done when**

* A sync with three edits makes one Postgres transaction, and the workspace lock is never held across a Postgres round trip.
* `GET /v1/workspaces/{id}` on an active workspace makes no `SETNX workspace:*:lock` call.
* `/metrics` shows the same or lower `postgres acquire` p95 and sweeper `max_lag` under `cmd/loadtest` with 50 polls at once.

+++ Detail: evidence and smaller findings

**Postgres under a lock**: `Service::save_state` (`src/sync/notes.rs:181`) runs `persist_edits` before `store.save_state`, inside `with_workspace_lock`. Each `record_edit` (`src/notes/workflow.rs:168`) is a transaction of 5 statements: a note lookup, `DELETE ... recorded_at < now() - 48h`, a receipt insert, a `note_stats` upsert and a `daily_edit_stats` upsert. When many workspaces close a sync in the same second, they all try to delete the same old receipt rows and wait on row locks. `Guard` renews the lock at most 6 times (`MAX_LEASE_RENEWALS`). A slow Postgres then turns into `LockLost` and a lost save.

**Reads that take a lock**: `service_view.rs:46` `enforce_deadlines` calls `take_lapsed_invite` (`invite_service.rs:349`, `with_workspace_lock`) on every read of an active workspace. Then `workspace()` calls `finalize_if_closed` (`store.rs:858`, `Guard`). One JSON view costs 2 lock acquisitions, 2 workspace GETs, 2 state GETs and 2 releases. `read_workspace_policy` allows 90 reads per minute per IP, so a laptop that keeps reconnecting can hold a workspace's lock against its own members.

**Views built twice**: 29 `broadcast` and `view_with_members` call sites in `service_lists.rs`, `service_invites.rs`, `invite_service.rs` and `service_settings.rs` follow the same pattern: change, broadcast, then build the view. Each `view_with_members` runs a `connected_members` EVAL, a `GET sync:` and a full decode.

**Lock loop**: `src/platform/cache/lock.rs:147` `acquire` calls `SetNX` every `LOCK_RETRY_INTERVAL` (20 ms) for up to `LOCK_WAIT_TIMEOUT` (3 s). Ten waiters on one queue lock make 500 Redis calls per second that do nothing. `poll_sync` holds the queue lock while it runs `drain_queue` and `fill_open_workspaces`, and that second call takes workspace locks too.

**Sweeper runs in order**: `scheduler.rs:75` calls `enforce_scheduled_deadline` one at a time, in batches of 100. One `complete_sync` with three Postgres transactions delays every other due workspace. `failed = true` and then `break` stop the whole tick after one `LockTimeout`.

**Connection defaults**: `deps.rs:66` sets only a tracer. The pool library defaults to `max_conns = max(4, num_cpus)`, with no lifetime and no idle timeout. The `POSTGRES_URL` pool and the `NOTES_POSTGRES_URL` pool both get the same default. The small hosted Postgres plan has a low connection limit, so this size is probably right by luck. Make it explicit.

**Smaller**:

* `Realtime::reserve_socket` (`realtime.rs:113`) adds up every client's count under `connections_mu` on each handshake. Keep a running total.
* `note_columns` (`notes/store.rs:41`) runs a `count(*) FROM note_flags` subquery per row. `sample` pulls 500 rows, so each cache refresh runs 500 subqueries. This is fine today, but it is the wrong shape for more notes. Join a grouped count.
* `sample` and `recent` use `ORDER BY random()`. This is fine at today's size. Write down the size, about 50,000 rows, where the code should switch to `TABLESAMPLE`.
* `queue_view` (`sync_queue.rs:903`) runs `get_ticket`, `LRANGE waits` and `ZCARD queue` on every poll. The wait estimate changes only when a batch forms, so cache it per queue for a few seconds.
* `Store::insert` makes 3 round trips: `EXISTS`, `SETNX` and an index sync. Fold them into one script, like the other writes.
* `observability::http` logs one info line per request. On a busy poll endpoint this line is most of the log volume. Think about logging only a sample of 2xx replies on `/v1/sync/poll` and `/v1/stats`.

**Not a problem**, I checked: the workspace hub uses one Pub/Sub connection per process. Presence uses lease-based scripts. `/v1/stats` is cached for 15 seconds. `open_workspaces_hub` folds bursts into one read per 250 ms. Redis scripts are fenced and make one round trip each. `PageCache` keeps the list view off Postgres after the first read per folder.

**Urgency**: medium. Nothing here fails at today's traffic. The Postgres path under a lock will fail first, when several workspaces close a sync in the same second.
