## In plain terms

When someone accepts an invite today, Demo App gives them access to two shared lists at once, but the app picks the lists. The person who sent the invite has no say in it. This feels wrong, and it can share a list that should stay private. This work lets the sender pick the lists, and it still finishes the invite if the sender never picks.

## Problem

An accepted invite grants 2, 1 or 0 lists by plan and writes the access rows at once. The server picks which lists: `next_shared_list` in `src/invites/accept.rs` takes the first list that the sender owns and that the new member cannot see yet. The count is right. The choice belongs to the sender.

## Rule for this repo

When the product gives a person a choice, the person sends a request and the server checks it. The server does not choose for them. The server owns the rule and the deadline, and the person owns the pick, in the same way `pick_home_list` splits them.

## What to do

* Add a share step: an accepted invite grants the sender a number of lists, and the sender picks them in the list view. Check each pick against the same rule that `next_shared_list` holds. Give the step a deadline, so one sender who never returns cannot leave the invite open forever. [DEMO-35](https://example.com/demo/issues/DEMO-35) shows the deadline shape.
* An invite from an admin script, or a share step that passes its deadline, keeps today's server-chosen fallback.

Pull request #60 merged with both review fixes as commit `2b3c4d5`. It applies the deadline shape from [DEMO-35](https://example.com/demo/issues/DEMO-35) to the share step only. The home list pick still has no deadline.

## Done when

The sender of an accepted invite picks which two lists the new member gets. The server refuses a pick that breaks the rule or comes from the wrong person. A pick that nobody makes still lands, so every invite ends with its lists shared.

+++ Detail: what is already in place

`src/invites/accept.rs` holds the whole rule set: `lists_by_plan` (2, 1 or 0), `unshared_lists`, `owned_by_sender` and `next_shared_list`. `resolve_invite` is the only caller. Only `finish_invite` reaches it, and `finish_invite` takes the completion lock first. So a share step can hang off a step that already runs exactly once.

`pick_home_list` is the model for the part the person owns. It checks the person's session, checks that it is their turn, checks the pick against the server's own rule, and refuses with an error and not with silence. Then it sends the whole sidebar to every laptop, not only the one changed list.

`WorkspaceView` already sends `step`, `invite` and `lists`. The app has all it needs to draw the sidebar and to know who must pick, with no new endpoint.

+++ Detail: implementation merged in pull request #60

`resolve_invite` now builds a share queue, `[sender, sender, admin]`, and does not write access rows. `set_share_queue` restarts the step clock, or calls `advance_invite` when the queue is empty. So `InviteState.step` stays on the resolved step for the whole share window. The app shows the share steps first, then waits the fixed delay.

`legal_shares(state, sender_id)` is now the only rule: lists the sender owns that the new member cannot see, else any list in the workspace. `next_shared_list` is now its first element and stays the fallback when a step lapses. Review fix `6f7a8b9` settles each departing member's earned shares through the same fallback, under the workspace lock, before it marks that member as gone. `settle_shares` removes those spent entries. It keeps the current deadline when the member who leaves is not the one picking, and it gives a fresh clock to a step that passes to someone else. `share_pickers` still skips members who are gone and stops at the number of free lists. But a member who leaves must settle earned shares before that filter can drop them. Service tests cover five ways to leave, in steps 1 and 8, and then finish the invite with every list shared and no step or deadline left open.

The server sends the step as `WorkspaceView.ShareStep`, with a time left, `ends_in_ms`, that it works out from the state on every view. A laptop that reconnects lands on the open step. The server also sends the step's `options`, so the app does not work them out again, because the rule depends on who owns what. `POST /v1/workspaces/{id}/share` is the part the sender owns. `sweep_due_shares` takes any step nobody spends, and admin scripts take theirs after `SCRIPT_SHARE_DELAY`.

In the app, the sidebar went from the home list only to every shared list. Each `ListMark` has an `is_home` flag, and a store key holds the server's pick options. `InviteScreen` sends a click in the sidebar to either the home list pick or the share step. Review fix `0c1d2e3` turns input back on for each new step, member and shares-left value, after it updates the sidebar and the options. A normal workspace update does not unlock a pick that waits for the server, so the sender can make both picks in a row and cannot send the same request twice.

This work does not cover two things. The banner shows no countdown for `ends_in_ms`. A step where every member times out still shares lists, as it did before this work.
