The React folders in Demo App have no clear plan yet. First, pick the folder layout that most single-page apps use. Then move and rename the files to fit it. Last, write the layout down as a rule that new code must follow.

## Current state

Every file sits under `web/src`. The only split is between pages and small UI parts. API calls, storage and hooks share one folder.

```
web/src/
  App.tsx
  components/
    SignInPage.tsx / .module.css
    LoadingNotes.tsx / .module.css
    NoteList.tsx / .module.css
    NoteScreen.tsx
    SettingsScreen.tsx / .module.css
    EmptyState.tsx / .module.css
    ui/
      Button.tsx, Card.tsx, LiveRegion.tsx, PageShell.tsx, TextField.tsx (+ .module.css each)
  lib/
    notes.ts         # API client + Note/NoteDraft types + share-link helpers
    session.ts       # localStorage persistence
    useSync.ts       # sync hook
    useRestoredNotes.ts # reload and resume hook
```

Links (branch `main`):

* [`App.tsx`](<https://example.com/demo-app/web/src/App.tsx>) switches views by hand, from `SignInPage` to `LoadingNotes` to `NoteScreen`. It has no router.
* [`components/NoteScreen.tsx`](<https://example.com/demo-app/web/src/components/NoteScreen.tsx>) shows `NoteList` or `SettingsScreen`, based on the current tab.
* [`components/ui/`](<https://example.com/demo-app/web/src/components/ui>) holds the design-system parts. It is already the cleanest folder.
* [`lib/notes.ts`](<https://example.com/demo-app/web/src/lib/notes.ts>) mixes fetch calls, the `Note` and `NoteDraft` types, and the helpers for share links.
* [`lib/session.ts`](<https://example.com/demo-app/web/src/lib/session.ts>), [`lib/useSync.ts`](<https://example.com/demo-app/web/src/lib/useSync.ts>), [`lib/useRestoredNotes.ts`](<https://example.com/demo-app/web/src/lib/useRestoredNotes.ts>)

The problems are easy to see. `lib/` holds everything that is not a component: storage, hooks, the API client and types. `components/` mixes small reusable parts with full screens. Nothing shows which files belong together. For example, `NoteList`, `useSync` and `notes.ts` are one feature, but they sit in two folders. The app has about 19 files today. It will grow soon, because `SettingsScreen` gets the invite flow from DEMO-31 next.

## Proposed structures (pick one)

### Option A: folders by feature (recommended)

Group files by the feature they belong to, not by file type. Keep a thin shared folder for parts that every feature uses.

```
web/src/
  app/              # App.tsx (composition and routing only)
  features/
    sign-in/
      SignInPage.tsx(+.module.css)
    notes/
      NoteScreen.tsx, NoteList.tsx(+.module.css), LoadingNotes.tsx(+.module.css)
      useSync.ts, useRestoredNotes.ts
    settings/
      SettingsScreen.tsx(+.module.css)
  entities/
    notes.ts          # Note/NoteDraft types + notes API client (used by every feature)
    session.ts        # stored session
  components/         # ui/ parts + EmptyState, unchanged
  index.css
  main.tsx
```

* **Benefits:** Each feature folder holds everything you touch to change that screen. The `settings/` folder can grow with the invite flow and stay tidy. A developer can move or delete a whole feature without a search through `lib/`. Most guides for mid-size React apps recommend this layout, so new people can learn it from public examples.
* **Drawbacks:** It adds folders, and the app is still small. Every feature uses `notes.ts`, so it needs a shared `entities/` folder. Someone must decide what counts as an entity and what counts as a feature. The move also changes import paths in almost every file.

### Option B: folders by file type, cleaned up (smallest change)

Keep the split by file type. Give each folder one job, so no folder is a catch-all.

```
web/src/
  pages/         # SignInPage, LoadingNotes, NoteScreen, NoteList, SettingsScreen (+ css)
  components/    # ui/ + EmptyState (reusable, display only)
  hooks/         # useSync.ts, useRestoredNotes.ts
  api/           # notes.ts (client + types)
  storage/       # session.ts
```

* **Benefits:** The change from today is the smallest. Developers who know older React templates know this layout. A new file has one obvious home, because the only question is what kind of file it is.
* **Drawbacks:** It does not fix the main problem. The note list and its sync hook still sit in different folders. It handles growth worse than Option A, once invites and sharing arrive. Each folder still collects unrelated files.

### Option C: atomic design (atoms, molecules, organisms, templates, pages)

* **Benefits:** Many people know the name. It has clear rules for small UI parts.
* **Drawbacks:** The line between an atom and a molecule is a matter of taste. The app has no large design system that needs these levels. The layout gives no home to API code or hooks, so the `lib/` problem stays. Teams often drop it once the app is bigger than a component library. I do not recommend it here.

## Recommendation

Pick Option A. `SettingsScreen` grows next, with the invite flow. Feature folders keep that new code inside `features/settings/`, instead of in `lib/`.

## Next steps (after you pick an option)

1. Confirm the option, or a variant of it.
2. Move the files, fix the imports, and update any path aliases in `tsconfig` and `vite.config`.
3. Write the layout down as a rule. Add a short "Project structure" section to the web README, so new components land in the right folder.
4. Run `pnpm lint` and `pnpm build` in `web/` to check that nothing broke.
